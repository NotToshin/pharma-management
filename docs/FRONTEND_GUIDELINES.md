# Frontend Guidelines

The UI is a Next.js App Router application in `frontend/`. Pages are large client components. They call the Express API with `apiFetch` and keep form state in React state. Read [UI_UX_GUIDELINES.md](./UI_UX_GUIDELINES.md) before changing layout or visual design, and [BACKEND_ARCHITECTURE.md](./BACKEND_ARCHITECTURE.md) before changing a request contract.

## Routing and navigation

App Router file routes. There is no `pages/` router and no custom `rewrites` in `next.config.ts`.

`frontend/middleware.ts` runs on all paths except `api`, static files, and `favicon.ico`. It redirects:

- `/` → `/dashboard` when a session cookie exists, otherwise `/login`
- `/login` → `/dashboard` when a session already exists
- any other path without a session → `/login?from=<path>`
- `/settings/rbac` without super-admin role or `ak_rbac=true` → `/dashboard?unauthorized=rbac`

The middleware cannot read `localStorage`. It trusts cookies `ak_session`, `refreshToken`, and the access-token cookie names. See [SYSTEM_OVERVIEW.md](./SYSTEM_OVERVIEW.md).

The sidebar (`frontend/components/app-sidebar.tsx`) is the product navigation. Groups match the module catalog. Items the user cannot `view` are filtered with `userCan`. Pharmacy client count replaces the hard-coded badge after `/api/clients` returns.

`routeTitleMap` in `frontend/app/layout.tsx` sets the header label and `document.title` (`AK-Pharma | <page>`). Add a new page to that map, to `navSections`, to `ROUTE_FEATURES`, and to `ALL_SYSTEM_MODULES` together.

`/doctors/timeline` and `/field-force/approvals` have page files and are absent from the sidebar and from `ROUTE_FEATURES`.

## Page and component organization

A page file is a client component (`"use client"`) that usually contains:

- local TypeScript interfaces for the API row
- `useState` for records, filters, dialog open flags, and the form
- a `fetchData` function called from `useEffect`
- create and edit `Dialog` or `Sheet` forms
- a `Table` of results
- `DeleteConfirmationModal` for deletes
- `toast` from `sonner` around every mutation

Extract a component when a second page needs it, or when the page already did (invoice form, purchase-order sheet, party settlement). Do not introduce a new state library for one screen.

### Naming

| Kind | Pattern | Example |
|---|---|---|
| Route page | `app/<area>/<screen>/page.tsx` | `app/sales/clients/page.tsx` |
| Feature component | kebab-case file, PascalCase export | `purchase-order-sheet.tsx` |
| UI primitive | kebab-case in `components/ui` | `button.tsx` exports `Button` |
| Hook | `use` prefix | `usePermission` |
| Validation | `<entity>Validation.ts` exporting `<entity>FormSchema` | `clientFormSchema` |
| Permission feature string | Exact module catalog label | `"Pharmacy Clients"` |

## State management

State is component-local `useState` plus `localStorage` for the session.

| Data | Where |
|---|---|
| Signed-in user, tokens | `localStorage` keys `user`, `ak_user`, `token`, `ak_token`, `refreshToken`, `ak_refreshToken` |
| Session flag for middleware | cookie `ak_session` |
| Permission refresh signal | `window` event `ak-permissions-updated` |
| List and form state | the page component |
| Theme | `next-themes`, forced to light by the layout |

`usePermission` reads the stored user once and subscribes to that window event. There is no global cache of server data. After a mutation the page calls its own `fetchData()`.

## API access

All authenticated calls should go through `apiFetch` from `frontend/lib/api.ts`.

```typescript
import { apiFetch, getEndpoint } from "@/lib/api"

const res = await apiFetch(getEndpoint("/doctors"), {
  method: "POST",
  body: JSON.stringify(validationResult.data),
})
```

`getEndpoint("/api/doctors")` and `getEndpoint("doctors")` both become `{base}/doctors`. `API_URL` is the normalized base.

`apiFetch` sets `Content-Type: application/json` and `credentials: "include"`. Login is the exception: `frontend/app/login/page.tsx` uses `fetch` so it does not require an existing access token.

Handle the response the way existing pages do:

```typescript
if (res.ok) {
  toast.success("Saved.", { id: toastId })
  fetchData()
} else {
  const errorData = await res.json().catch(() => null)
  toast.error(errorData?.message || "Server failed to save the record.", { id: toastId })
}
```

The success payload is `json.data`. Paginated lists also return `json.meta`. Some pages still accept a raw array if `data` is missing. Prefer `const payload = json.data ?? json` when touching an old caller.

`cache: "no-store"` is passed on some GETs. That is a fetch init field. Next.js data cache is not used, because these are client fetches.

There is no `services/` API layer on the frontend. The page calls `apiFetch` directly.

## Data fetching

Pattern on list pages:

1. `loading` state true.
2. `apiFetch` the collection.
3. Store `data` in state.
4. Filter and search in memory on many screens (doctors, clients).
5. Server query params (`page`, `limit`, `searchTerm`) exist for modules whose backend schema defines them. The doctors list route validates those query fields. Check the matching `*Routes.ts` before assuming every page paginates on the server.

`frontend/components/ui/pagination.tsx` is the shared pager UI. Use it when a screen already slices a list. Do not add a second pager component.

Empty lists render an in-table or in-card message inside the page. There is no shared empty-state component.

## Forms and validation

Forms are controlled inputs. There is no form library.

Schemas that exist today:

| File | Schema | Used by |
|---|---|---|
| `lib/validations/doctorValidation.ts` | `doctorFormSchema` | `app/doctors/database/page.tsx` |
| `lib/validations/clientValidation.ts` | `clientFormSchema` | `app/sales/clients/page.tsx` |
| `lib/validations/doctorVisitLogValidation.ts` | `visitLogFormSchema` | `app/field-force/visit-logs/page.tsx` |

Other screens validate with local `if` checks and `toast.error` before posting. The RBAC page requires name, email, and password, and requires password length of at least 6, without a shared Zod schema. The login page checks that email and password are non-empty, then relies on the API.

Backend Zod in `backend/src/validations/` is the security boundary. Client schemas improve the message shown before the request. They do not protect the API. Several backend modules have schemas with no frontend twin. Keep the two copies aligned when both exist.

### Field rules that are actually encoded

Doctors (`doctorFormSchema`):

- `doctorName`, `phone`, `bmdcRegNumber`, `specialtyAndInstitute`, `chamber`, `tier`: non-empty strings
- `email`: required and `z.string().email("Invalid email format")`
- `patientVolumeDaily`: coerced integer ≥ 0
- `territory`: optional string
- `territoryAndMio`: optional, default `"Unassigned"`

Clients (`clientFormSchema`):

- `pharmacyName`, `phone`, `territory`: required strings
- `creditLimitBDT` and `outstandingBalanceBDT`: coerced numbers ≥ 0
- `creditTermDays`: coerced integer ≥ 0, default 30
- `status`: enum `Active / Healthy`, `Credit Hold`, `Watchlist`, `Cash Only`

Visit logs: required operational strings in `visitLogFormSchema`. Read that file before editing the visit form.

Login (API `loginSchema`): email format, password `min(1)`.

User provisioning (API `provisionUserSchema` and the RBAC page): email format, password `min(6)`, required name and role code.

Phone numbers are required strings. There is no regex for Bangladesh numbers. Password strength beyond length 6 is not implemented. Numeric money fields should use `z.coerce.number()` because inputs yield strings.

### How a new form should be built

Follow the doctors page (`handleAddDoctor` in `frontend/app/doctors/database/page.tsx`).

1. Add `somethingFormSchema` under `frontend/lib/validations/` if the payload is reused or has more than one constraint. Mirror it in `backend/src/validations/` as `{ body: somethingFormSchema }` when you add the endpoint. If the backend schema already exists, match it.
2. Keep one `useState` per field, or one object, consistent with the surrounding page.
3. On submit, `preventDefault`, clear previous field errors, and `safeParse` the payload.
4. Map `issues` into a `Record<string, string>` keyed by `issue.path[0]` and `setFormErrors`. Show the message under the input. Fire `toast.error` with a short summary.
5. Start `const toastId = toast.loading("…")`.
6. `apiFetch` JSON of `validationResult.data` so coerced numbers are the values you send.
7. On `res.ok`, `toast.success` with the same `id`, close the dialog, and reload.
8. On failure, `toast.error(errorData?.message || "…", { id: toastId })`.
9. Deletes open `DeleteConfirmationModal`. Do not call `window.confirm` or `alert`.

Sketch:

```typescript
const parsed = clientFormSchema.safeParse(formData)
if (!parsed.success) {
  const errorsMap: Record<string, string> = {}
  parsed.error.issues.forEach((issue) => {
    errorsMap[issue.path[0]?.toString() || "form"] = issue.message
  })
  setFormErrors(errorsMap)
  toast.error("Form validation failed. Please check the highlighted fields.")
  return
}

const toastId = toast.loading("Saving pharmacy client...")
const res = await apiFetch(getEndpoint("/clients"), {
  method: "POST",
  body: JSON.stringify(parsed.data),
})
```

Updates on the doctors page use `doctorFormSchema.partial().safeParse`.

Server validation errors arrive as `message` plus optional `errors: [{ field, message }]`. The current pages surface `message` in the toast. Field-level server errors are not automatically painted back onto inputs.

## Loading and submission states

| Situation | Implementation |
|---|---|
| First paint of the shell | Layout returns “Loading...” until `mounted` |
| Session check | “Authenticating secure session...” |
| Login request | Button shows `Loader2` and disables while `loading` |
| Mutations | `toast.loading`, then success or error with the same id |
| Delete modal | `isDeleting` disables the confirm button and shows a spinner |
| Lists | Page-local `loading` flags and `Skeleton` where a page imported it |
| Forbidden module | Rose panel in the layout, link back to `/dashboard` |

Do not use the browser `alert()` for API results.

## Authentication in the UI

`frontend/lib/auth.ts` is the session helper.

- `setAuthSession` writes the 7-day `ak_session` cookie, 15-minute access cookies, refresh cookie, role cookie, `ak_rbac`, and `localStorage`.
- `logout()` calls `POST /api/auth/logout` with the bearer token and `x-user-*` headers, then clears storage and redirects to `/login`.
- `isTokenExpired` decodes the JWT payload and treats the token as expired 5 seconds early.
- `ensureFreshAccessToken` in `api.ts` is single-flight so parallel requests rotate the refresh token once.

The root layout also redirects to `/login` on the client if `isAuthenticated()` is false. That runs in addition to middleware.

Profile edits in the account dialog update React state and `localStorage` only. Email, role, and territory inputs are disabled. There is no profile API.

## Protected routes and role-based UI

Three layers, all implemented:

1. **Edge middleware** checks that some session cookie exists. Only `/settings/rbac` has a role check here.
2. **Layout** uses `featureForPath` and `userCan(user, feature, "view")`. A false result replaces `children` with the access-denied panel. Unknown paths are allowed.
3. **`PermissionGate`** and `usePermission().can(feature, action)` hide buttons. Actions are `view`, `create`, `edit`, `delete`, and `special`. `view` maps to the API field `read`. Overview cards use `overview:<key>` and read `overviewGrants`.

Super admins always pass `userCan`. A user with no stored permission rows also passes, so a session that lost its matrix is not locked out. Once rows exist, a missing module is denied.

Wrap a create button:

```tsx
<PermissionGate feature="Doctors List" action="create">
  <Button>Add doctor</Button>
</PermissionGate>
```

`feature` must be the catalog string, not a made-up slug.

## File upload

Excel:

1. `<input type="file" accept=".xlsx,.xls">`.
2. `XLSX.read` on an `ArrayBuffer`.
3. Map rows to the bulk-import JSON shape.
4. `POST` to the module’s `/bulk-import` endpoint with `apiFetch`.
5. Toast success or the server `message`.

Doctors and clients implement this. Empty sheets and missing required columns toast an error and do not call the API.

Avatar upload reads an image as a data URL and stores it on the local user object. It is not sent to the server.

## Pagination, filtering, and search

List pages filter with local state (`search`, territory, status) using `Array.filter` over the fetched rows. Where the backend supports it, pass `searchTerm`, `page`, and `limit` as query parameters instead of downloading every row. Doctors, clients, audit logs, and RBAC users have query schemas. Confirm the route before adding a query key the validator will strip or reject.

Search is case-insensitive substring matching in the page, not a dedicated search engine.

## Code practices

- Prefer the existing UI primitives in `components/ui` over new HTML widgets.
- Import the `cn` helper from `@/lib/utils` or `cn`. Both point at the `cn` package. UI primitives import `cn` directly.
- Keep API paths in `getEndpoint`. Do not hard-code `http://localhost:5000` in a page.
- Mutation feedback uses Sonner. Delete confirmation uses `DeleteConfirmationModal`.
- Do not add a dependency for a single form or for data fetching. The app is already consistent without React Hook Form and React Query.
- `next build` currently ignores TypeScript errors. Still type new code. Avoid new `any` unless the surrounding page already uses it for permission JSON.
- Client components are the default for screens that fetch in the browser. The root layout is a client component, so it cannot export `metadata`. The title is set in an effect.

## Error handling checklist

| Source | What the user sees |
|---|---|
| Zod `safeParse` failure | Field map plus toast |
| HTTP error JSON | `message` toast |
| Thrown fetch | “Network error…” toast |
| 401 after refresh fails | Redirect to `/login?expired=1` inside `apiFetch` |
| 403 page permission | Layout access-denied panel |
| Empty data | Inline empty copy on that page |
